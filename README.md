# CREWAI

Ten CrewAI projects served by one FastAPI application, with a website that explains and runs each of them.

- **Backend:** FastAPI (`app.py`), CrewAI 1.x, Google Gemini through an API key.
- **Routes:** `/agent1` to `/agent10`, one route for each project. Each route takes a valid input and returns a valid output.
- **Website:** the same server returns a single-page website at `/`. It shows, for every project, its score on the *complexity versus precision* graph, how every point was given, the code cut into the **seven steps** of the CrewAI notes, and a panel that runs the agent.
- **API documentation:** `/docs` (generated by FastAPI).

Four projects are **Crews** (agents and tasks) and six are **Flows** (steps, routers and branches).

## How the server works

1. `app.py` creates one `LLM` from the environment variable `GEMINI_API_KEY` (the Colab notebook used `userdata.get(...)` for the same purpose).
2. Each project is written in the order of the **seven steps** from the notes. For a Crew these are Setup, LLM, Agent, Task, Crew, Run and Result. For a Flow they are Setup, LLM, State, Start, Steps, Run and Result. The comments `#---Step 3: Agent(...)` in `app.py` mark where each step begins.
3. Every route validates its input with a Pydantic model and returns a Pydantic model, so a bad request is refused with a clear `422` message and a good request always receives a response of a known shape.
4. Every input field has a default, so an **empty request is also a valid request**: it runs the project on a built-in sample.
5. Every response contains `trail`, the list of agents or Flow methods that ran, in order.
6. At most two runs execute at the same time, which keeps the free Gemini limit from being exceeded. A third request waits for a free place.

### Calling a route

```bash
# 1. Describe the agent: its input schema and an example input (fast, no model call)
curl https://YOUR-SERVICE.onrender.com/agent1

# 2. Run it on the sample input from a browser
https://YOUR-SERVICE.onrender.com/agent1?run=true

# 3. Run it with your own input
curl -X POST https://YOUR-SERVICE.onrender.com/agent1 \
     -H "Content-Type: application/json" \
     -d '{"topic": "Home battery storage"}'

# 4. POST with no body at all also runs the sample input
curl -X POST https://YOUR-SERVICE.onrender.com/agent1
```

A short text field can be overridden in a browser with a query string, for example `/agent1?topic=Solar%20panels`.

### 1. Blog Post Crew (`/agent1`)
**Problem.** A researched blog post takes hours of searching, drafting and editing. **How it works.** A *Researcher* searches the web with a DuckDuckGo tool and lists facts with their sources. A *Writer* drafts about 600 words using only those facts. An *Editor* compares each claim with the research notes, deletes what is not supported and saves `blog_post.md`. The three tasks run in order (`Process.sequential`) and each receives the earlier results as `context`. **Output.** The topic, the final blog post and the `trail`.

### 2. Competitor Analysis Crew (`/agent2`)
**Problem.** Tracking what competitors ship, charge and say takes hours every week. **How it works.** Four agents (*Site Scraper*, *Pricing Analyst*, *News Analyst*, *Strategist*) work under a manager model (`Process.hierarchical`, `manager_llm`). The tasks name no agent, so the manager decides who does each one. The scraper reads the pages with `ScrapeWebsiteTool`; the pricing analyst writes `not found` where a page gives no price; the strategist produces a SWOT report. **Limit.** Pages drawn by JavaScript return little text and are reported as `page not readable`. The notes draw the three specialists as working in parallel, but CrewAI's hierarchical process hands out one task at a time. Marking the tasks `async_execution=True` did not make them overlap in a test, so this project does not claim parallel work.

### 3. Meeting Notes Crew (`/agent3`)
**Problem.** After every meeting someone must write the summary and chase action items. **How it works.** Three agents read the transcript file at the same time (`async_execution=True`): one writes a five-line summary, one lists action items, one lists decisions. A *Formatter* waits for all three through `context` and assembles `notes.md`. Because one agent cannot run two tasks at the same moment, each parallel task has its own agent. The action items use `output_pydantic`, so they are returned as a validated list of owner, task and due date.

### 4. Data Report Crew (`/agent4`)
**Problem.** Turning weekly sales CSV files into a readable report is slow and repetitive. **How it works.** A *Data Analyst* must call a pandas tool (`Sales Stats`) and return the figures as a validated `SalesStats` object (`output_pydantic`). An *Insight Writer* writes three findings from those figures. A *Reviewer* re-runs the tool and corrects any difference. Finally, plain Python recomputes four totals and compares them with the analyst's figures (`code_check`, `all_figures_match`). **Input.** CSV text with the columns `date, region, product, units, unit_price`.

### 5. Customer Support Flow (`/agent5`)
**Problem.** Tickets arrive mixed together and must be read, sorted and sent to the right person. **How it works.** `@start receive_ticket` fills the state from the ticket (`ticket_id`, `customer_name`, `issue_description`; `satisfaction_score` stays 0, as in the notes); `categorize_ticket` makes one direct model call that returns one of five categories (validated); `@router route_by_category` returns `billing`, `account_access` or `other`; `handle_billing` and `handle_access` set the priority to high, and `handle_other` covers technical and feature requests, all in Python; `or_(...)` starts `resolve_ticket`, which drafts a reply that promises no refund or date. No Crew is used.

### 6. Resume Screening Flow (`/agent6`)
**Problem.** One job post brings hundreds of resumes. **How it works.** `load_resumes` loads a resume, and the route starts a new Flow for each one. `score_resume` scores it from 0 to 10 using only the resume text. `@router check_score` applies the rule `score >= 7` in Python, so the same resume always receives the same decision. A shortlisted resume goes to a summary Crew (strengths and gaps); the others receive a drafted rejection. `or_` runs `save_results`, which adds a row to `results.csv`.

### 7. Bug Triage Flow (`/agent7`)
**Problem.** Issues pile up without labels, so urgent bugs sit beside feature requests. **How it works.** `classify_issue` returns `bug`, `feature` or `question`; `@router route_type` starts exactly one Crew. The *bug* Crew rates the severity (validated) and writes reproduction steps; the *feature* Crew writes a user story with acceptance criteria; the *question* Crew answers from a documentation page it reads. `or_` runs `post_reply`, which builds labels such as `type:bug` and `severity:high` in code. Nothing is posted anywhere.

### 8. Content Repurposing Flow (`/agent8`)
**Problem.** One long article should become a LinkedIn post, a tweet thread and a newsletter section. **How it works.** `extract_points` returns the title, audience, tone and key points (validated). Three listeners on that step start three Crews side by side (LinkedIn, six-tweet thread, newsletter). A timing test with three slow model calls showed all three running at once; `and_(...)` waits for all three, and `publish_pack` saves three files (`linkedin_post.md`, `twitter_thread.md`, `newsletter.md`). `load_article` reads a web address with `ScrapeWebsiteTool` when `url` is given, and uses the pasted text otherwise. Code then checks that every tweet is 280 characters or fewer and that the LinkedIn post is near 150 words.

### 9. Lead Qualification Flow (`/agent9`)
**Problem.** Sales teams waste time on cold leads while hot leads wait. **How it works.** An enrichment Crew reads the company website and returns a validated profile. `@router score_lead` rates the lead `hot`, `warm` or `cold`. If the website could not be read, code rates the lead `cold` without asking the model. Only a hot lead receives an outreach Crew that drafts a first email; a warm lead is added to a list; a cold lead is archived. `or_` runs `log_lead`, which adds a row to `leads.csv`. Nothing is sent.

### 10. Approval Report Flow (`/agent10`)
**Problem.** Auto-generated reports are risky to publish unchecked, but reviewing every word is slow. **How it works.** `review_draft` carries the real `@human_feedback` decorator from the notes. Its console prompt cannot work on a web server, so it uses a small provider that pauses the Flow instead (`HumanFeedbackPending`), and `kickoff` returns at that point with the draft. The person's decision arrives with the next call, where `@router check_decision` sends it to `publish_report` (which saves `final.md`) or to the Revision Crew, which returns to `review_draft`. The Flow is therefore split over two calls.
1. Send `topic` and `audience`. A Research Crew (researcher, analyst, fact checker) collects sourced claims and a Writing Crew drafts a report. The response has `status: "awaiting_review"` and the `draft`.
2. Send the same `topic` and `audience`, the `draft`, and a `decision`: `"approved"` returns `status: "published"` and the `final` text; `"revise"` with `feedback` starts a Revision Crew and returns a new draft for review again.

## Complexity versus precision

The notes score every use case from 1 to 10 on two axes and place it in one of four regions (1 to 4 is low, 5 to 10 is high):

| | Low precision | High precision |
|---|---|---|
| **High complexity** | Complex Crews | Flows orchestrating Crews |
| **Low complexity** | Simple Crews | Flows with direct LLM calls |

The points are not guessed. They are counted from the design of each project:

- **Complexity points** = number of each element × its weight: agent 2, task 1, tool 1, flow step 1, router 3, extra parallel branch 2, Crew inside a Flow 2, manager agent 4, human gate 4, loop 3, structured model 1. The score is the points divided by 4, rounded and kept between 1 and 10.
- **Precision points** = the safeguards present: structured output 20, code does the exact work 20, grounded in a source 15, independent check 15, constrained routing 10, human approval 20. The score is the points divided by 10, rounded and kept between 1 and 10.

For example, project 1 has 3 agents (6), 3 tasks (3) and 2 tools (2): 11 points, which is 2.75 and rounds to a complexity of **3**. It has a search tool (grounding, 15) and an Editor (independent check, 15): 30 points, a precision of **3**. That is the Simple Crews region. The website shows this working for every project.

These scores describe how each project is designed. They are not measurements of accuracy. Project 4 lands in the region the notes assign to Flows with direct LLM calls; it remains a Crew because the notes list it as one, and its precision comes from code (pandas and a final check), not from the agents.

## Run it locally

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export GEMINI_API_KEY="your key from Google AI Studio"
uvicorn app:app --reload
```
Open `http://127.0.0.1:8000/` for the website and `http://127.0.0.1:8000/docs` for the API.

## Deploy on Render

Create a **Web Service** from this repository with these settings.

| Setting | Value |
|---|---|
| Language | Python 3 |
| **Build Command** | `pip install -r requirements.txt` |
| **Start Command** | `uvicorn app:app --host 0.0.0.0 --port $PORT` |
| Health Check Path (optional) | `/health` |

| Environment variable | Value |
|---|---|
| `PYTHON_VERSION` | `3.12.8`. Required: CrewAI supports Python 3.10 to 3.13, and a new Render service may default to a newer version. |
| `GEMINI_API_KEY` | Your Google AI Studio key. Mark it secret. |
| `GEMINI_MODEL` | Optional. Default `gemini/gemini-3.1-flash-lite-preview`. |

The public link is `https://<your-service>.onrender.com`. The website is at `/`, and the routes are `/agent1` to `/agent10`. On Render's free plan the service stops after 15 minutes without traffic and needs about a minute to start again, and a run makes several model calls, so a route can take a minute or more to answer.
